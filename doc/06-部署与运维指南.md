# 06 部署与运维指南

## 1. 环境要求

| 组件 | 版本建议 | 说明 |
| --- | --- | --- |
| Node.js | ≥ 18（本项目实测较新版本） | 前后端各自 `npm install` |
| npm | ≥ 9 | 需网络拉取依赖 |
| MySQL | **8.x** | 因 `ai_*` 表使用 `utf8mb4_0900_ai_ci` 排序规则 |
| nginx | 1.x（可选，生产推荐） | 提供反代/SSL；宝塔面板亦可 |

## 2. 目录与端口规划

| 应用 | 目录 | 内置端口 | 对外端口（nginx） |
| --- | --- | --- | --- |
| 后端 API | `backend/` | 3003 | `/api`、`/uploads` 由 nginx 反代 |
| 前端 Next.js | `frontend/` | 3001 | 前台 443；后台 23080 |
| 数据库 | — | MySQL 3306 | 仅内网 |

## 3. `.env` 字段说明（复制 `.env.example` → `.env`）

| 分组 | 键 | 说明 |
| --- | --- | --- |
| 数据库 | `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD` | 连接 `mysql2` 连接池 |
| JWT | `JWT_SECRET` | access token 签名密钥，请用随机长串 |
| | `JWT_EXPIRES_IN` | access token 有效期（如 `15m`） |
| | `REFRESH_TOKEN_EXPIRES_DAYS` | refresh token 有效期天数（默认 30） |
| Keycloak SSO | `ADMIN_PANEL_ORIGIN` | SSO 成功后回跳的后台 origin（生产填 `https://<后台域名>:23080`；留空则按请求头推导） |
| 端口 | `BACKEND_PORT` | 后端端口（默认 3003） |
| | `FRONTEND_PORT` | 前端端口（默认 3001，与 Next 启动一致） |
| | `API_BASE_URL` | 前端访问后端的基地址 |
| 环境 | `NODE_ENV` | `development` / `production`（影响 refresh Cookie 的 `secure`） |
| 站点资料 | `SITE_NAME` / `SITE_DOMAIN` / `ICP_NUMBER` | 站点名/域名/备案号 |
| 上传 | `UPLOAD_PATH` | 上传目录（默认 `./uploads`） |
| | `MAX_FILE_SIZE` | 上传上限；当前 `.env` 为 `unlimited`；可写 `10MB` |
| 邮件 | `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASS` / `FROM_EMAIL` | nodemailer 发信（联系表单/通知用，可选，也可在后台配置） |
| 安全 | `CORS_ORIGIN` / `RATE_LIMIT_WINDOW` / `RATE_LIMIT_MAX` | CORS 与显式限流参数（注：`server.js` 内另有按 token 角色的分级限流） |

> Keycloak 的连接配置（`ISSUER_URL`/`CLIENT_ID`/`CLIENT_SECRET`）**在后台「登录管理」页填写**，存数据库 `auth_methods.config`，改完即时生效；Keycloak 客户端的 Valid redirect URIs 填该实例的独立回调地址 `https://<后台域名>:23080/api/auth/keycloak/<方法key>/callback`（登录管理页可直接复制）。

> 存量 `.env` 中的 `DB_NAME=pailink`、`SITE_NAME=深圳市电湃科技有限公司` 为当前生产配置；**请勿在版本库各环境间复制带真实密码的 `.env`**。

## 4. 数据库初始化

```bash
# 1) 建库建账号（示例库名 pailink，按需更换）
mysql -uroot -p -e "CREATE DATABASE IF NOT EXISTS pailink DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci; CREATE USER IF NOT EXISTS 'pailink'@'localhost' IDENTIFIED BY 'PASSWORD'; GRANT ALL ON pailink.* TO 'pailink'@'localhost'; FLUSH PRIVILEGES;"

# 2) 导入表结构（纯建表，无 seed）+ 幂等多语言迁移块
mysql -upailink -p pailink < ./init.sql
```

> `init.sql` 现已为**纯建表结构，不含任何 seed 数据**，且内置幂等增量迁移块：
> - **全新部署**：建好全部表 + 默认「中文」语言行。
> - **旧配置服务器**：把 `init.sql` 运行一次即可对齐多语言结构（补 `lang`/`source_id` 列、改联合唯一、建 `languages` 表等），**只增量新增、绝不覆盖/删除既有数据**；可重复运行无副作用。
> - 说明：`init.sql` 不再含 mysqldump 的临时视图工件，任意账号都能一路执行；建议用带 `CREATE`/`ALTER` 权限的账号导入。
> - 首次部署后无后台账号/页面/站点资料，请到后台手动配置并创建管理员账号。

## 5. 本地开发

```bash
# 后端（3003）
cd backend && npm install && npm run dev      # nodemon src/server.js

# 前端（3001，-H 0.0.0.0）
cd frontend && npm install && npm run dev     # next dev -p 3001
```

联调通过 `http://localhost:3001`（前台）与后台 `http://localhost:3001/admin`（开发时 Next 直接暴露，无需 nginx）。API 基地址由 `.env` 的 `API_BASE_URL` / 前端 `utils/api.ts` 决定。

## 6. 生产部署

### 6.1 构建
```bash
cd frontend && npm run build && npm run start   # next start -p 3001
cd backend && npm start                          # node src/server.js (3003)
```
建议用 `pm2` 或 systemd 守护两个进程（3001 / 3003）。

### 6.2 nginx 反代（两套模板见仓库根目录）

**`tech-website.conf`（通用版）**：前台走 80 端口并 `deny /admin`；后台走 23080 端口，反代 `/`、`/api`、`/uploads` 到 3003。适合未上 HTTPS 的内网/演示部署。

**`tech-website-BTpanel.conf`（宝塔版）**：前台 443 强制 HTTPS（`server_name` 与 SSL 证书路径需替换）；在目录内额外放行 `/admin` 相关信令端口 23080 的 `ck-umd` 资源；含安全头、gzip、针对 `jpg|png|webp|svg` 的缓存规则。

| nginx 参数 | 值 |
| --- | --- |
| 前端 upstream | `http://localhost:3001` |
| 后端 upstream | `http://localhost:3003` |
| 后台安全 | 前台 server 块 `location /admin { deny all; }` |
| 上传大小 | `client_max_body_size 0;`（解除限制） |
| 资源缓存 | 图片 30d；CKEditor `ck-umd` 需正确 `Content-Type` |
| 客户端缓存 | 浏览器缓存体系见 [07](./07-浏览器缓存与弱网回退.md)：版本校验接口 `GET /api/content/status`、前端 `utils/dataCache.ts`、图片 Service Worker `public/sw.js`（`/sw.js` 由 Next 从 `public/` 提供、nginx `location / → 3001` 已覆盖，**无需**改反代；加载 SW 需 HTTPS 或 localhost，宝塔版用 443 HTTPS 满足） |

### 6.3 静态资源落地检查（部署后）
- `/uploads/*` → 应可访问用户上传文件。
- `/system-default/*` 与 `/uploads/system-default/*` → 内置素材（SVG/图标/图片）。
- `/ck-umd/*` → CKEditor 前端静态资源。
- `/sw.js` → 应能返回 Service Worker 脚本（由 Next `public/` 提供，浏览 HTTPS/localhost 时注册生效；`middleware.ts` 已将其排除在语言路由中间件外）。
- `GET /api/content/status?lang=zh` → 应返回 `{navigation, settings, news, languages}` 时间戳（浏览器缓存的前端版本接口，健康可用性检查）。

## 7. SSL 证书（如启用 HTTPS）

宝塔版模板默认用 Let's Encrypt（`/www/server/panel/vhost/letsencrypt/...`）；需替换 `server_name`、证书目录、并确认 80→443 重写。安全头已在模板内置（HSTS、X-Frame-Options、nosniff、Referrer-Policy）。

## 8. 日常运维

- **进程守护**：`pm2 start process.yml`（或 systemd unit），自启动 + 崩溃重启。
- **备份**：定时 `mysqldump pailink` + 备份 `backend/uploads/`（用户素材）与 `frontend/.next` 可不必备（可重建）。
- **密钥管理**：轮换 `JWT_SECRET` 会使现有 access/refresh token 立即失效，请选择维护窗口执行。
- **安全建议**：生产收紧 body 上限（当前 `500mb` 过大）、收紧限流阈值、移除 `routes/auth.js` 的调试 `console.log` 明文密码打印、移除空依赖 `"all"`、清理 `*.tsx_bak` 备份文件。

## 9. 健康检查与排障

- `GET /api/health`：确认后端存活。
- 数据库异常：检查 `.env` 的 `DB_*` 连通与账号权限。
- 前台 302 不到首页：`pages/home` 的 `published` 是否为 1，及 slug 是否 `home`。
- 上传 413：检查 nginx `client_max_body_size` 与 `express.json` 限制。
- 后台 404/被拒：确认走 23080 端口而非前台 443（前台 `/admin` 被 `deny`）。

## 10. Tag 自动部署（Forgejo Actions）

当往内网 Forgejo（`forgejo.pbt.lan`）推送一个新 **tag**（如 `v1.2.0`）时，Forgejo Actions
自动执行部署流水线：runner 构建前端 → rsync 同步源码与产物到生产服务器 → 服务器端安装生产
依赖 → `pm2 reload` 前后端 → 健康检查，实现"打完 tag 即自动发布"。

**架构**（工作流定义见 `.forgejo/workflows/deploy.yml`）：

```
推 v* tag 到 forgejo
  → Forgejo Actions：runner（Forgejo 宿主机，host 直连模式，Node 20）
      1. actions/checkout 检出代码
      2. frontend: npm ci + next build
      3. rsync 同步源码 + .next 产物 → 生产服务器 /www/wwwroot/pailink
         （先备份服务器端 frontend/.next → .next.bak 供快速回滚）
      4. 服务器端：backend/frontend 各执行 npm ci --omit=dev
      5. pm2 reload pailink-backend / pailink-frontend
      6. 健康检查：curl 127.0.0.1:3001 与 127.0.0.1:3003/api/health
```

**部署源**：`ssh://git@forgejo.pbt.lan:2222/zhuzhaoting/Pailink_OfficialWebsite.git`
（生产服务器访问不了内网 Forgejo，因此代码由 CI 主动推送，而非服务器拉取。）

**与旧方案的关系**：Gitee（`shenzhen-dianpai/official-website`）降级为**纯代码镜像**，
其 webhook 与 Pailink_Deploy 服务（:3005）已退役，仅作观察保留；tag 会同步推到
Gitee 以维持镜像一致，但 Gitee 不再触发部署。

**轻量 CI**：`.forgejo/workflows/ci.yml` 在 master 分支推送 / PR 时只跑前端构建检查，
尽早暴露构建错误；正式发布仍由 tag 触发的 `deploy.yml` 完成。

**一次性配置**（Forgejo 与 runner 同在 NAS 的 Docker 中；生产 = 公网云服务器，CI 以 root SSH 登录）：
1. Forgejo 开启 Actions：编辑 Forgejo 容器数据卷中的 `app.ini`（通常为
   `<数据卷>/gitea/conf/app.ini`），加 `[actions] ENABLED = true`，重启容器；
   仓库 Settings → Actions 启用。
2. NAS 上以 SSH 构建一次 CI 作业镜像（node20 + rsync；自建镜像同样会出现在绿联 Docker
   管理页的镜像列表里，可正常管理）：
   ```dockerfile
   # /volume1/docker/pailink-ci/Dockerfile
   FROM docker.m.daocloud.io/library/node:20-bookworm
   RUN apt-get update && apt-get install -y --no-install-recommends rsync \
       && rm -rf /var/lib/apt/lists/*
   ```
   ```bash
   cd /volume1/docker/pailink-ci && sudo docker build -t pailink-ci:node20 .
   ```
   注意：首次运行工作流时 runner 还需联网拉取 `actions/checkout@v4`（来自 code.forgejo.org，
   之后缓存在 runner 的 data 目录），NAS 需有公网出口。
3. NAS 上以 Docker 容器部署 forgejo-runner（docker 模式，挂载 docker.sock）：
   - 获取注册令牌：Forgejo 网页 → 站点管理 → Actions → Runners → 创建（或仓库级
     Settings → Actions → Runners）。
   - 目录规划（按 NAS 实际路径调整，下同）：`/volume1/docker/forgejo-runner/{data,workspace,config.yml}`。
   - `config.yml` 关键项：
     ```yaml
     runner:
       # Forgejo 经 Caddy 以本地自签 CA 提供 HTTPS，需跳过证书校验
       insecure: true
       labels:
         - 'deploy:docker://pailink-ci:node20'   # runs-on: deploy → 用该镜像跑作业
     container:
       # 关键：作业工作目录路径必须与 NAS 宿主机完全一致，否则作业容器挂载不到工作区
       workdir_parent: /volume1/docker/forgejo-runner/workspace
     ```
   - `docker-compose.yml`：
     ```yaml
     services:
       forgejo-runner:
         image: code.forgejo.org/forgejo/runner:latest   # 建议固定为 releases 页最新稳定版
         container_name: forgejo-runner
         restart: unless-stopped
         volumes:
           - /volume1/docker/forgejo-runner/data:/data
           - /volume1/docker/forgejo-runner/config.yml:/config.yml
           # workspace 以相同宿主机路径挂回容器（配合上面的 workdir_parent）
           - /volume1/docker/forgejo-runner/workspace:/volume1/docker/forgejo-runner/workspace
           - /var/run/docker.sock:/var/run/docker.sock
         command: forgejo-runner daemon --config /config.yml
     ```
   - 注册（一次性）：`docker compose run --rm forgejo-runner forgejo-runner register
     --instance https://forgejo.pbt.lan --token <注册令牌> --name nas-runner --insecure`，
     然后 `docker compose up -d`。
4. NAS 上生成部署密钥 `ssh-keygen -t ed25519`（有 SSH 的机器上执行均可），公钥追加到
   生产 `root` 的 `~/.ssh/authorized_keys`。
5. 仓库 Settings → Actions → Secrets 配置：
   `DEPLOY_SSH_KEY`（私钥全文）、`DEPLOY_HOST`（生产公网 IP）、
   `DEPLOY_KNOWN_HOSTS`（`ssh-keyscan -p <端口> <生产IP>` 输出，首次部署后立即配置以固定主机指纹）。
6. 生产服务器 root 全局 npm 源设为 `https://registry.npmmirror.com`（加速服务器端 `npm ci`）。
   （工作流容器内的 npm 源与 rsync 安装已写在 `deploy.yml` 的步骤里，无需额外配置。）
7. 确认退役：连续 2–3 次 Forgejo 部署成功后，`pm2 delete pailink-deploy` 并移除 Gitee webhook。

**发布**：本地 `git tag v1.2.0` 后运行 `node push.js`（tag 会推到 forgejo 触发部署），
在 Forgejo 仓库的「Actions」页观察流水线进度。注意一次只推一个 tag（工作流已用
`concurrency` 串行化，并发推送会排队）。

**回滚**
- 快速回滚（前端构建问题）：服务器上
  `cd /www/wwwroot/pailink/frontend && rm -rf .next && mv .next.bak .next && pm2 reload pailink-frontend`。
- 完整回滚（代码问题）：本地对上一个正常 commit 打一个**新的** patch tag（如 `v1.2.1`）并推送，
  重新走部署流程。不要重复推送同名 tag。

**要点**
- ⚠ **rsync `--delete` 会删除部署目录中仓库未跟踪、且不在排除清单内的任何文件**——比旧的
  `checkout -f` 更严格：部署目录内手改的文件将被清除。请勿在生产目录手工改文件。
- `.env` 与 `backend/uploads/` 由工作流中的 `--exclude` 保护，**严禁移除这些排除项**，
  否则用户上传数据会在下次部署时被清空。
- node_modules 不随 CI 传输（backend 依赖原生模块 sharp，必须服务器端安装）；
  依赖更新通过服务器端 `npm ci --omit=dev` 完成，需要服务器能访问 npm 镜像源。
- 构建端（runner）与生产端 Node 版本需保持一致（当前均为 20）。
